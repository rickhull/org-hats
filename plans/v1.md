# org-hats v1 development plan

**Status:** Plan for review. Nothing here starts implementation.

This plan turns [docs/quartermaster_redesign.md](../docs/quartermaster_redesign.md)
("the architecture doc") into ordered, verifiable work for the 0 → 1 release.
It supersedes the "1.0 core freeze" item in [roadmap.md](roadmap.md): 1.0 no
longer means freezing the v0.4 surface. It means shipping the authority
subsystem as one clean breaking version — rough edges accepted.

Two external facts shape the ordering:

1. **Quartermaster's first milestone is an MVP demo of org-hats**, built
   against the in-memory path through the same consumer interface. Their work
   is theirs; our job is that the portable seam is consumable early. The
   critical artifact is therefore an **alpha tag as soon as one vertical path
   works** (evidence → admission → envelope → verify → `mayAct`), not the
   polished 1.0.
2. **We may want our own Cloudflare demo** — a reference deployment in
   `org-hats-cloudflare` that proves the paved road without borrowing
   Quartermaster's app. It comes after the portable release, not before.

## Scoping decisions

- **1.0 = the portable packages only**: evolved core, authority engine with
  the in-memory adapter, neutral access verifier, conformance inventory,
  testing subpath. Shipped from this repository as one `org-hats` package
  with subpath exports.
- **`org-hats-cloudflare` is a separate package at its own 0.x cadence.** The
  authority Worker, Durable Objects, ops entrypoints, and the demo land there
  after 1.0. Its roughness never blocks the portable release.
- **A fresh `v1` branch** carries the work, per the architecture doc; `main`
  remains the v0.4 line. The v0.4 tags and their `OH-QM-01…11` ids stay
  untouched — the new conformance inventory gets a new id scheme.
- **Explicitly not in 1.0** (recorded to resist scope creep):
  - OIDC/passkey/local-login helpers (identity adapters are runtime surface;
    the demo uses a dev-evidence stub);
  - restore drills, registry, vanity tooling, deployment automation;
  - multiple signature algorithms (one: Ed25519 via WebCrypto, behind the
    internal signer seam);
  - anything only a hypothetical second consumer would ask for.
- **Release mechanics**: version `1.0.0`, a migration note
  (`docs/migration-v1.md`) recording the 0.4 → 1.0 deltas, a README rewrite
  stating the honest "portable semantics, one reference runtime" positioning,
  and `SECURITY.md` (stewardship requires the disclosure policy before the
  code protects production data). **Distribution stays out of the npm
  ecosystem for now — decided.** The git tag is the release, exactly as for
  v0.4: the consumer pins `git+https://codeberg.org/rickhull/org-hats.git#v1.0.0`.
  Registry publication (npm or JSR) is revisited only if a second consumer
  asks for it; nothing in this plan depends on it.

## Dependency graph

```
M0 fences ──► M1 interface spec ──(consumer review gate)──►
   M2 core (pure) ──► M3 authority (in-memory) ──► M4 access verifier
                                                        │
                              M5 conformance ◄──────────┘
                                │  ├─ alpha tag early (vertical path)
                                │  └─ 1.0.0 tag at completion
                                └─► M6 org-hats-cloudflare ──► M7 demo
```

M2 can start against draft M1 types; M3 must wait for the reviewed spec. M6
depends on M3's internal adapter seam, not on M4/M5 finishing — but it is
scheduled last anyway because the consumer's milestone does not need it.

## Milestones and tasks

Verification for every task: `pnpm check` passes (extended per M0 to run the
v1 suites), repo stays buildable, and the new behavior is proven through the
interface the task introduces — never through a private seam the conformance
inventory cannot see.

### M0 — Branch, workspace, fences

- [ ] **T0.1 Fresh branch and package layout.** Create `v1` from `main`.
      Convert to a pnpm workspace if needed for the later Cloudflare package;
      the portable package stays the repo root with subpath exports
      (`./authority`, `./access`, names final in M1). Existing root and
      `./node` exports keep compiling. *Acceptance:* `pnpm check` and
      `pnpm typecheck` pass on `v1` with the layout in place; no behavior
      change. *Scope:* S.
- [ ] **T0.2 Extend the compiler fence and adopt a test runner.** The
      runtime-neutrality fence (`tsconfig.core.json`, `types: []`) grows a
      second configuration covering `src/authority` and `src/access`: no
      Node-only types, no Cloudflare imports. Adopt `node:test` (zero new
      dependencies) for the v1 suites and wire it into `bin/check`. CI rule
      written down: portable suites must run green without workerd or a
      Cloudflare account. *Acceptance:* a deliberate bad import in
      `src/authority` fails `pnpm check`; a sample `node:test` file runs in
      `bin/check`. *Scope:* S.

### M1 — Interface specification pass (the open decisions)

- [ ] **T1.1 Authority types.** Write the normative
      `AuthorityRuntime` surface as TypeScript plus a short spec section:
      `PrincipalEvidence`, `AccessIssue` (envelope + refresh-handle outcome:
      kept/rotated/revoked), `RefreshInput`, `AuthorityContext`,
      `AuthorityCommand` union (initial set: participation invite/accept/
      revoke, admission and access requests, grant/revoke, hat selection,
      actor disable), `CommandResult`, and the closed failure taxonomy
      (unavailable, unauthenticated, not-admitted, expired, wrong interface
      version, wrong operation/site binding, invalid signature). Idempotency
      keys on mutating commands. *Acceptance:* the types compile inside the
      fence and are importable from a subpath; every failure kind has a
      doc line naming who owns the product response. *Depends:* T0.1.
      *Scope:* M.
- [ ] **T1.2 Envelope format.** Versioned v1 claims (operation binding,
      site bindings and aliases, org actor ids, selected hat actions/reach,
      readable org and exceptional team ids, iat/exp, key id, interface
      version), canonical JSON encoding, Ed25519 via WebCrypto behind the
      internal signer seam. *Acceptance:* a written format doc; fixed test
      vectors defined (serialization, expiry, wrong version, wrong binding,
      forged signature, key rotation). *Depends:* T1.1. *Scope:* M.
- [ ] **T1.3 Policy-bundle vocabulary.** The smallest vocabulary the two
      design twins need: actions, roles, role-to-action mapping, read policy
      — validated by pure functions, applied by authority when computing read
      reach before issuance. *Acceptance:* two bundles (one per twin) validate
      and are rejected on malformed input. *Depends:* T1.1. *Scope:* S.
- [ ] **T1.4 Synthetic twins as data.** Define the Professional Operation
      (persistent, multi-site, multi-organization) and the Festival
      (time-bounded, multi-venue, ~150 short-lived teams) as public fixtures:
      organizations, actors, sites, teams, hats, grants. Real customer names
      appear nowhere. *Acceptance:* fixtures load as plain data and exercise
      multi-organization participation and site independence structurally.
      *Depends:* T1.3. *Scope:* S.

**Checkpoint — consumer review gate.** Quartermaster reviews the spec before
M3 hardens it: their MVP demo is built against exactly this surface, so
post-M1 changes must be additive or re-reviewed. Record their accepted
interface/envelope version range.

### M2 — Core model evolution (pure)

- [ ] **T2.1 Organization freed from the operation root.** An organization
      participates in many operations; an actor is `(organization_id,
      actor_id)`; operation grants name that pair; primary/default hats are
      operation-local. Pure transitions and invariants, no storage.
      *Acceptance:* twin fixtures typecheck against the evolved model; the
      0.4 → 1.0 model deltas are drafted into the migration note.
      *Depends:* T1.4. *Scope:* M–L (split if needed).
- [ ] **T2.2 Policy-bundle validation and read-reach computation.** The pure
      functions that validate a bundle and compute readable organization and
      exceptional team ids under it. *Acceptance:* property tests over
      generated grant shapes; every allow/deny reason enumerated and tested.
      *Depends:* T1.3, T2.1. *Scope:* M.

### M3 — Portable authority engine, in-memory

- [ ] **T3.1 Internal adapter seam.** The capabilities the engine needs —
      atomic commit, trustworthy clock, signer, idempotent command claims
      with payload check, audit co-committed with its fact, outbox records —
      as an internal (unexported) interface plus its in-memory
      implementation with an injectable virtual clock and deterministic
      signer. *Acceptance:* the engine's unit tests run fully deterministic;
      no adapter type is exported from any public subpath. *Depends:* M1.
      *Scope:* M.
- [ ] **T3.2 Participation workflow.** Invite → accept → active → revoke as
      an idempotent message workflow across the two in-memory coordinators,
      with visible partial states and retry. *Acceptance:* scenario tests
      prove partial-failure recovery, duplicate-message safety, and the
      canonical "operation records active" rule. *Depends:* T3.1, T2.1.
      *Scope:* M.
- [ ] **T3.3 Admission, grants, hat selection.** Access requests, admission,
      grant/revoke, worn-hat selection and fallback as typed commands with
      idempotency and audit. *Acceptance:* every command has allow and deny
      cases keyed to the failure taxonomy. *Depends:* T3.2. *Scope:* M.
- [ ] **T3.4 Evidence resolution and issuance.** `accessFromEvidence`
      resolves a principal to an active organization actor with wearable
      hats and signs an envelope; actor disable blocks new issuance
      immediately; `refresh` returns the explicit handle outcome and revokes
      affected refresh records on grant changes. *Acceptance:* disable and
      revocation propagate exactly as the architecture doc's bounded-window
      rules state. *Depends:* T3.3, T1.2. *Scope:* M.

### M4 — Neutral access verifier

- [ ] **T4.1 Verify and expose.** Envelope verification (signature, issuer,
      interface version, expiry, operation/site binding) yielding
      `NeutralAccess` facts; fail closed on unknown versions. *Acceptance:*
      a consumer maps a product fact onto a neutral target and gets correct
      allow/deny without ever seeing raw claims. *Depends:* T1.2, T3.4
      (issuer to test against). *Scope:* S–M.
- [ ] **T4.2 Fixed vectors.** The T1.2 vector list as golden tests,
      including key rotation and rolling verifier-first upgrade semantics.
      *Acceptance:* vectors pass and are committed as data. *Depends:*
      T4.1. *Scope:* S.

### M5 — Conformance inventory and the release

- [ ] **T5.1 The inventory as executable twins.** New id scheme (not
      `OH-QM-*`); the twins run end-to-end against the in-memory authority
      through the public interface only: every allow/deny reason, reach
      edges, fallback order, one organization actor in two operations,
      read reach under each twin's bundle, invite/accept/revoke, idempotent
      retry. *Acceptance:* the inventory is the executable specification —
      a case that cannot be expressed through the public interface is a
      design bug, not a test gap. *Depends:* M3, M4. *Scope:* L (scenario
      batches).
- [ ] **T5.2 Invariant and generative tests.** Arbitrary valid states,
      duplicate commands, reordered messages, partial workflow failure.
      *Acceptance:* generators run in CI without network or accounts.
      *Depends:* T5.1. *Scope:* M.
- [ ] **T5.3 Release.** Migration note, README rewrite, `SECURITY.md`,
      version `1.0.0`, tag, pin handed to the consumer. *Acceptance:*
      `pnpm check` green from a clean clone with no Cloudflare tooling;
      migration note covers every 0.4 → 1.0 break. *Depends:* T5.1.
      *Scope:* S.

**Early alpha tag inside M5:** as soon as one vertical path works
(T3.4 + T4.1 + the twins' happy path), tag `v1.0.0-alpha.1` so
Quartermaster's MVP demo can pin something before the full inventory lands.
Additive-only changes after that tag; anything breaking re-reviews with the
consumer.

### M6 — `org-hats-cloudflare` reference runtime

- [ ] **T6.1 Package scaffold and workerd harness.** New workspace package;
      integration tests using the real local runtime, no mocked Cloudflare
      APIs. *Acceptance:* a trivial DO test runs in CI (this package's CI
      may use workerd; the portable packages' CI does not). *Depends:* M5
      (internal seam stable). *Scope:* M.
- [ ] **T6.2 OrganizationAuthority DO.** SQLite schema, migrations, audit
      co-commit, sealed identity-provider configuration shape.
      *Acceptance:* the participation workflow (T3.2) passes against real DO
      storage. *Depends:* T6.1. *Scope:* L.
- [ ] **T6.3 OperationAuthority DO.** Sites, teams, hats, grants, policy
      version, refresh records; alarms and outbox retry; bounded
      housekeeping. *Acceptance:* the full internal conformance inventory
      runs against the Cloudflare adapter. *Depends:* T6.2. *Scope:* L.
- [ ] **T6.4 Runtime and ops entrypoints.** The authority Worker's service
      binding surface; typed ops commands (`bootstrap`, `schemaStatus`,
      `exportSnapshot`); signing-key rotation with verifier-first ordering.
      *Acceptance:* rolling rotation passes in workerd; no raw SQL or
      generic exec anywhere in the surface. *Depends:* T6.3. *Scope:* M.

### M7 — The Cloudflare demo

- [ ] **T7.1 Self-contained demo.** A demo worker in the package: bootstrap
      a synthetic twin through ops commands, a dev-evidence stub standing in
      for a real identity adapter, envelope issuance through the authority
      runtime, verification through the access package, and a minimal page
      or API showing allow/deny per `NeutralAccess`. Runs in `wrangler dev`
      with zero external dependencies; optional `*.workers.dev` deployment
      notes. *Acceptance:* a fresh clone reaches a working demo with the
      documented commands and no Quartermaster code. *Depends:* T6.4.
      *Scope:* M.

## Checkpoints

- **After M1:** spec reviewed and version ranges accepted by the consumer —
  the gate that keeps their MVP demo from building on churn.
- **Alpha tag:** vertical path works; consumer unblocked for the demo.
- **After M5 (1.0.0):** portable release cut; consumer pilot wiring proven
  against the in-memory authority.
- **After M7:** paved road demonstrated end to end without the consumer.

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Interface churn after Quartermaster builds against the alpha | High | M1 consumer review gate; additive-only after `v1.0.0-alpha.1`; breaking changes re-review |
| Envelope design gold-plating | Medium | One algorithm, one version, fixed vectors early (T1.2); the format doc is a v1 decision, not a forever decision |
| Policy vocabulary grows to a general policy language | Medium | Twin-driven only; anything the twins don't exercise is rejected in review |
| M6 Durable Object work balloons | Medium | It is a separate 0.x package; its scope never gates 1.0; DO tasks sized L and split further when started |
| Dual maintenance of v0.4 line and `v1` | Low | v0.4 is frozen at tags; `main` only takes fixes if the consumer asks before cutover |
